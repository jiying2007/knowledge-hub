# A123X 三板打包只读审计

范围：CB400、F20 DEVWIRE、F20 EVT1 的模块迁移/安装/加载、EXT4、USB升级容器、SWU、Recovery与分区映射。只读工程审计，未修改源码、重跑固件构建或操作设备。

镜像身份：CB400使用.tmp/build-evidence/01-A123X_CB400_NonSip_LP5X_8GB_SPI-Nor_16MB_eMMC_8GB/firmware；DEVWIRE使用.tmp/devwire-dhd-header-fix/rebuild-current-20261022-ready/firmware；EVT1使用.tmp/devwire-dhd-header-fix/boards/02-A123X_F20_EVT1/firmware。对应build.json完成时间分别为2026-10-22 01:22:48、02:42:26、02:12:22 UTC。CB400和EVT1镜像早于本轮SSH规则变化，不能据此断言当前配置产物已验证。

## 原因

release-tool/env/include/fsimage.mk的FSIMAGE_REMOVE_LIB_MODULE在打包前无条件清空/lib/modules。git blame表明该逻辑来自供应商提交143a8b7e（2026-04-23），不是本轮修复新增。SDK内核阶段先modules_install到/lib/modules，再通过common_drivers/amlogic_utils.sh迁移模块到/amlogic/modules，生成ramdisk/vendor安装脚本。rootfs的rcS通过这些脚本加载模块，因此/lib/modules是供应商原流程中的中间目录。

build.sh先kernel再vendor。F20 DHD由vendor阶段安装到/lib/modules/<release>/extra，此时内核模块迁移已结束；后续fsimage删除/lib/modules，导致新模块未迁移即被删除。其安装时depmod成功不等于最终镜像模块存在。CB400 W1U直接安装到/amlogic/ext_modules，未受此次删除影响；EVT1当前未选DHD。

## 已确认发现

1. P1 DEVWIRE模块交付契约不一致：最终镜像无bcmdhd.ko，尽管驱动编译、modpost和安装曾成功；f20-wifi-load调用默认/sbin/modprobe bcmdhd。kmod默认查询/lib/modules/<uname>，SDK原生模块路径/amlogic/modules并不自动成为其索引根。因此只拷贝ko到amlogic也不足以修复，需要同步安装、依赖与加载契约。Wi-Fi默认disabled，显式启用才会触发加载失败。
2. P1 三板升级防混刷缺口：三份SWU都使用software.version=1.0.1和hardware-compatibility=[1.0]，使用同一recovery公钥；当前swupdate-2019.11-emmc/.config关闭CONFIG_HW_COMPATIBILITY，对应check_hw_compatibility编译分支直接返回0。USB platform.conf也只区分C5/A123X芯片族。未见三种板型之间的包适配检查；同签名源不等于同板型兼容。属于缺少防混刷约束，未执行真实跨板升级。
3. P2 当前三板SSH包增量构建缺口：Makefile.tools仅根据board/pc目录是否存在决定是否构建全部工具；缓存存在时先执行*-aml-rootfs-install，不保证新增Dropbear已构建。DEVWIRE已实际复现缺缓存二进制而失败，手动make -C platform/tools dropbear后恢复。当前三板defconfig都启用AML_SSH，另外两板是源码适用性判断，未重建复现。
4. P2 Recovery DTB配置不兑现：三板都配置AML_OTA_DTB，但该变量除定义/配置外未被打包规则消费。Makefile.ota:210实际使用AML_KERNEL_DTB。三份boot与recovery内DTB逐字节一致。CB400声明的专用recovery DTB未生效；DEVWIRE/EVT1目前两个变量相同，暂无当前值差异。未据此断言recovery无法启动。
5. P2 三板SWU存在未消费logo payload：文件清单包含logo.img，但sw-description仅声明system、boot、recovery、bootloader四个更新项，logo没有更新动作，也无对应描述哈希。当前OTA不会通过这份描述更新logo；USB包另有logo分区项。若logo无需OTA更新，应移出SWU以消除歧义。

## 风险与非发现

三板USB GPT的backup LBA均为16777215，即配置总容量8589934592字节（8 GiB）。system为第8分区、2 GiB；SWU目标p8/p6/p3与GPT的system/boot/recovery一致。未发现rootfs超分区。但实际标称8GB eMMC的可用LBA、烧录器是否重定位备份GPT没有设备证据，容量适配须独立验证，不能将8GB与8GiB等同。

曾怀疑生成sw-description的sha256行缺分号会导致解析失败。已依据实际libconfig-1.7.2/lib/grammar.y证伪：setting_terminator允许为空。因此不列为缺陷。

## 已验证通过

三个rootfs的选定ELF可执行入口及递归DT_NEEDED依赖、解释器扫描未发现缺失；三个Recovery分别扫描9个入口/依赖对象未发现缺失。未覆盖所有dlopen插件和设备运行。

三份SWU的四项描述哈希均匹配；稀疏rootfs完整展开hash与保存的2 GiB EXT4相同；boot和bootloader与各板inventory一致；每份SWU签名均可用自身Recovery内的公钥验证。三份USB容器hash匹配inventory、厂商-c检查通过；解包后的boot/recovery/system/bootloader与同板SWU逐项hash一致。

工程证据：.tmp/three-board-package-audit/20261022T030850778763Z.log；recovery/20261022T031326271221Z.log；usb/20261022T031501513186Z.log。所有工具执行回执与日志hash均保留。审计脚本成功仅代表检查执行完成，不代表发现清零或产品放行。

## 建议修复顺序

先统一DHD的最终目录与显式加载契约，并增加最终镜像模块/依赖检查；优先适配SDK的外置模块机制，不整体删除清理hook。随后修工具包缓存依赖，再补三板板型/版本适配门禁；明确Recovery DTB和logo更新策略。每次以实际镜像内容及USB/SWU一致性验收。容量、启动、联网、Recovery OTA与断电恢复保留给板端验证，不由本次Host审计替代。
