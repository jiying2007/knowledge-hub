## 主要发现

### R1 / P1：SC5336P 共享库有两个构建和安装 owner

- 位置：`release-tool/components/Makefile:25`、`:43`；`linux/mbp/sensor/smartsens_sc5336p/Makefile:13`；`release-tool/env/include/rules.mk:140`；`release-tool/build.sh:714`、`:723`。
- components 重新编译 SDK sensor 源码并安装 `/usr/lib/libsns_sc5336p.so`；SDK 原生 sensor 阶段随后再编译并安装同名库。
- 已复现：现有 target 库与原生 sensor 库使用 SDK strip 后的结果完全一致；components 候选有 SONAME，target 最终库无 SONAME，说明 components 候选被后续安装覆盖。
- 影响：组件验证的候选与最终交付库不是同一产物；编译选项、链接属性和依赖可能随入口及安装顺序变化。当前并没有证据证明两者已发生函数 ABI 不兼容，不能把“不同 hash”直接解释成运行崩溃。
- 建议：Sensor 共享库只由既有 `linux/mbp/sensor` 规则构建/安装；通用诊断工具引用它，不重新承担同一库的交付职责。验收比对最终 target/镜像库与唯一构建 owner 的产物。

### R2 / P2：F20 聚合的并行安装存在同输出目录重复构建

- 位置：`release-tool/projects/f20-modules/Makefile:9`、`:18`、`:20`。
- `install` 的两个独立前置项 `all` 和 `install-components` 都递归调用 components，使用同一个 OUT。
- 已复现：空输出目录下 `make -n -j8 ... install` 打印两条写入同一个 `libsns_sc5336p.so` 的编译命令；其他通用组件也由两个子 make 分别调度。
- 影响：直接并行安装时可能同时写同一 ELF。正式 SDK 先 all 后 install 的既有顺序可使输出预先存在，不能据此认定独立安装安全。
- 建议：建立单一依赖链，先统一 build，再进行不触发第二次并发 build 的 install；补空 OUT 的并行安装回归。

### R3 / P2：关闭 Sensor 选择仍会被 F20 聚合编译和安装

- 位置：`release-tool/env/mk/Makefile.vendor:50`、`:52`；`release-tool/components/Makefile:12`、`:25`、`:43`。
- SDK 原生 sensor/sample 使用 AML_SENSOR_SC5336P，但 F20 聚合无条件调用全部 components，也没有向组件安装规则传递并落实同一选择。
- 已复现：传入 `AML_SENSOR_SC5336P=n` 的安装 dry-run 仍编译、安装 libsns_sc5336p.so 及相关诊断工具。
- 影响：配置关闭不能排除该功能的制品，声明配置与打包内容不一致。默认仍不启用采集，这不是默认开机即启动相机的问题。
- 建议：由现有 SDK 功能选择控制唯一 owner 的编译和安装；单独定义诊断工具选择，避免产品名替代组件开关。

### R4 / P2：通用驱动、运行路径及 Kconfig 仍被产品名和来源工程名绑定

- 位置：`release-tool/projects/f20-dhd/Makefile:30`、`:34`；`source-lock.json:9`；`projects/f20-modules/wifi/f20_wifi_load.c:35`；`release-tool/env/platform/configs/Config.in:86`；`common_drivers/Kconfig.ext_modules:3`。
- `/lib/firmware/f20/f10-dhd`、`Use F10 vendor DHD with TCPKA for F20 DEVWIRE`、AML_F20_WIFI_DHD 和内核 AMLOGIC_F20_WIFI_DHD 都将产品/来源混入通用驱动接口。
- SDK 已有 Wi-Fi 固件直接安装至 `/lib/firmware` 的规则，以及按驱动划分的数据目录；将路径改到标准父目录仍不能声明已完整遵循 SDK 原布局。
- `projects/f20-modules` 可以保留产品选择和启动策略；`projects/f20-dhd` 中的通用驱动、固件和构建职责应通过既有 Wi-Fi/vendor 模块体系组织。跨仓迁移若需要新 manifest 项，应单独设计，不直接搬目录制造未受管理源码。
- 建议：配置使用 BCMDHD/器件能力命名；最终路径按 SDK 安装约定及驱动取文件要求确定，统一改安装、驱动、loader、清单、测试。F10 的提交、版本和 hash 保留为 provenance，不抹掉来源记录。产品 `/etc/f20` 元数据和模式选择可保留，不应一刀切删除所有产品命名。
- 上一轮这部分规范整改不完整，新 SDK-INTEGRATION.md 也把自定义路径写成了范例，需要一并修订。

### R5 / P2：已退役的 native/brcmfmac 分支仍影响当前产品构建

- 位置：`projects/f20-modules/Makefile:9`、`:12`、`:25`；`env/platform/configs/Config.in:73`。
- all 无条件验证旧 CYW43012/brcmfmac 参考固件，即使实际选择的是另一套 DHD 四件套；非 DHD 安装还复制旧参考固件到 `/usr/share/f20/wifi/cyw43012-f10`。
- AML_F20_WIFI_NATIVE 是无 prompt、default n、无上游 select 的隐藏 bool。隔离 Kconfig 验证确认，单独在 defconfig 写 y 会被恢复为 n；源码帮助文案仍描述原生驱动功能。
- 影响：当前产品依赖不用的旧参考制品；目录、示例、帮助与实际运行路径分裂。DHD 选择时旧参考固件不会被上述分支安装，不能误报为当前 DHD 镜像已混装。
- 建议：正式构建仅校验所选 bundle。历史参考候选移出默认构建和安装契约；隐藏遗留开关及相关接线明确退役，或补齐真正可用的独立选择和加载实现。

### R6 / P1：SC5336P 的 MBP 适配绕过内核 I2C 地址占用检查

- 位置：`linux/mbp/sensor/smartsens_sc5336p/sc5336p_mbp.c:128`，以及 `reg_read/reg_write`。
- MBP adapter 打开 `/dev/i2c-N` 后直接执行 I2C_RDWR，没有先执行 I2C_FUNCS/I2C_SLAVE；而新增 ID、stream、rx 诊断入口会先检查能力并用 I2C_SLAVE 拒绝内核已绑定的地址。
- 本 SDK `drivers/i2c/i2c-dev.c:409` 明确只在 I2C_SLAVE 分支执行 i2cdev_check_addr；I2C_RDWR 分支不会代做同一检查。
- 新增临时 Host 负例将 I2C_SLAVE 定义为返回 EBUSY：实际 MBP adapter 没有调用它，仍发生 193 次模拟寄存器写入并报告 error=0。没有访问真实设备。
- 影响：当同地址已由内核驱动拥有时，MBP 路径仍可能写入该设备；各入口的 owner 契约不一致。
- 建议：适配器在第一条寄存器访问前落实能力和内核地址占用检查；失败关闭 FD、保持未初始化。另行定义用户态进程之间的独占机制，不能把 I2C_SLAVE 当成跨用户态进程互斥锁。

### R7 / P2：产品 profile 的安装责任仍混入通用 sample

- 位置：`linux/mbp/sample/pipeline_demo/Makefile:179`。
- 通用 `config*.json` 通配安装会把新增 config_f20_sc5336p.json 安装到所有选择该 sample 的产品；同处又硬编码 CB400 defconfig 来覆盖默认 config.json。
- 影响：F20 package 不是产品 profile 的唯一安装入口，非 F20 产品也会携带 F20 profile；通用 sample 的行为直接依赖具体板名。当前 F20 profile 保持 enable=0，不因此推导自动采集。
- 建议：通用 sample 保留通用数据安装；具体产品由 defconfig/rootfs/vendor profile 规则选择默认配置及专属模板。
