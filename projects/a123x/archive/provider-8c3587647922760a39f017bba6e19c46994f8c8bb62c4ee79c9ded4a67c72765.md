## 1. 配置建议

**标准版：若明确限定2D激光SLAM＋视觉检测＋云端语音对话，建议以4GiB LPDDR4X＋16GB eMMC为成本基线；端侧AI版：若要在这些功能并发时常驻约1–2B量化语言模型，建议8GiB＋32GB。**

如果只做一套硬件、希望同时覆盖上述两种产品方向，优先评估8GiB＋32GB。当前算法尚未冻结，不应把4GiB当作覆盖视觉SLAM和任意本地LLM的统一规格。

用户进一步询问2GB是否足够：**2GiB可作为“有界2D激光SLAM＋轻量视觉＋云端对话”的成本优化候选，当前没有证据证明满足，也没有实测证据证明绝对不够。** 第5.3节给出1440MiB目标预算和准入条件；默认4GiB建议是降低实现/峰值风险，不是宣称物理最低容量必为4GiB。

| 产品/算法场景 | DDR建议 | eMMC建议 | 适用条件与结论 |
|---|---:|---:|---|
| 成本优化：有界2D激光SLAM＋轻量检测＋云端对话 | 2GiB条件候选 | 仍建议16GB；8GB仅受控bring-up | 需达到第5.3节目标及完整并发/异常验收，当前不能直接冻结量产 |
| 2D激光SLAM＋检测/跟随＋1080p视频/TF录制＋云端对话 | 4GiB | 16GB | 需约束扫描/图节点/队列、无常驻LLM；实测关闭后才可冻结 |
| 视觉/视觉惯性SLAM，或较重ROS2/中间件＋同等业务 | 8GiB | 16GB起，地图/资源增长则32GB | 4GiB按本预算已不足25%余量；不包含无限关键帧/三维重建 |
| 2D SLAM＋约1–2B INT4语言模型、4k上下文 | 8GiB | 32GB | 单模型、KV按FP16/BF16预算，转换/时延/功耗另测 |
| 视觉SLAM＋约1–2B INT4语言模型 | 8GiB作为受限候选，复杂图/框架则16GiB评估 | 32GB | 必须限地图、关键帧、上下文及并发；不能把8GiB当所有VSLAM保证 |
| 约4B INT4语言模型与SLAM/媒体并发 | 16GiB评估档 | 32GB起，更多离线资源/地图则64GB | 8GiB按本预算不满足25%余量；16GiB料号/布线/训练仍须SoC owner确认 |
| 7B以上、多LLM、多模态编码器/稠密三维重建 | 单独立项，不纳入上述承诺 | 按资源包另算 | 容量即使装得下，也未证明时延、CPU/NPU覆盖、带宽及电池续航可行 |

DDR的“4/8/16GiB”使用二进制容量；eMMC“16/32GB”是市场标称档位，实际用户区需读EXT_CSD/块设备容量，不能直接等同于16/32GiB。

## 4. DDR预算方法：避免漏算和重复算

使用物理容量口径：

```text
R_peak = 固件/不可映射保留容量 + Linux/服务物理占用
       + 池外媒体与NPU工作区 + 音频/UI/网络应用
       + SLAM/导航峰值 + 同时发生的瞬态

建议物理DDR >= R_peak / (1 - 25%)
```

25%是本次工程余量策略，不是芯片规范或已批准阈值。增长更快、碎片多或模型未定时应增加，不把这25%误称为全部MemAvailable。

- PMZ/CMA等整池已计入保留预算时，池内SDK/NPU/媒体buffer不再按同一物理页重复相加；只另计池外副本、额外池和用户态权重/工作区。
- 对同一dma-buf使用共享物理页，多个进程RSS相加会重复；进程PSS也无法完整反映no-map、驱动或所有DMA池。采样要结合`/proc/meminfo`、PSS、实际DTB、媒体池和dma-buf导出统计。
- reusable CMA不等于永久不可用，普通页空闲也不保证能分配大块连续DMA；同时验CMA空闲及最大分配/碎片行为。
- 对模型mmap，页缓存和映射是同一物理页时不再加一份；运行库解包/量化转换/拷入设备池会产生额外副本，需要观察实际实现。
- eMMC/TF不能代替实时DDR。不得用向eMMC持续swap掩盖导航/媒体内存不足；zram占DDR和CPU，也不创造物理容量。

dma-buf共享机制参考[Linux内核文档](https://docs.kernel.org/driver-api/dma-buf.html)。本篇没有声称当前厂商驱动已按某一种共享策略实现。

## 5. 基础业务与SLAM的DDR明细

以下都是**工程预算上限候选，未实测**，按原生C/C++生产服务而非完整开发桌面/可视化环境估算：

| 项目 | 预算MiB | 假设及后续检查 |
|---|---:|---|
| Linux内核、基础服务 | 384 | 不含下列独立业务及固定保留区；核Slab、内核栈、共享库/PSS |
| 固件/no-map/security等保留 | 384 | 以当前350MiB PMZ＋11MiB secmon等为起点；最终DTB/启动修正可能改变 |
| 池外媒体/CMA额外缓存 | 128 | PMZ内buffer已由上一行覆盖；包括池外副本和其他实际活跃池 |
| 视觉模型及用户态推理工作区 | 384 | 固定少量检测/跟随网络；不含本地LLM和大多模态编码器 |
| 音频AFE/云语音链路 | 128 | 本地AEC/降噪/唤醒和有限缓冲；重型离线ASR/TTS需另加 |
| 双屏UI | 64 | 两屏RGB565双缓冲原始像素约0.44MiB，其余是UI/字体/资源/缓存 |
| 应用、网络、云连接等 | 256 | 并发连接、队列/栈/业务缓存必须限额 |
| 基础小计 | **1728** | 不是当前板PSS或MemTotal测量 |
| 2D激光SLAM/导航峰值 | **768** | 预算含图、扫描、局部/全局规划、回环优化；必须限历史与队列 |
| 视觉/视觉惯性SLAM/导航峰值，替代上一行 | **1536** | 图像金字塔、特征/关键帧、地图点/词袋及优化；不含无限稠密重建 |
| 启动/恢复/流式OTA等并发瞬态 | **256** | OTA大包落持久介质并流式处理，不全包放DDR；若需更大临时池重算 |

计算结果：

| 场景 | 峰值MiB | 含25%空闲后的容量需求 | 结论 |
|---|---:|---:|---|
| 基础＋有界2D SLAM＋瞬态 | **2752** | **3.58GiB** | 4GiB有条件可行；2GiB不足以按该并发预算交付 |
| 基础＋有界视觉SLAM＋瞬态 | **3520** | **4.58GiB** | 建议8GiB |
| 2D场景再加1024MiB框架/容器/中间件 | **3776** | **4.92GiB** | 建议8GiB；1024仅敏感性预算，不是ROS2统一内存规格 |

主要误差来源是实际SLAM图大小和模型/媒体池，不能因为总表数字低于4GiB就冻结BOM。4GiB标准版应在完整并发和异常峰值下证明预算成立。

### 5.1 为什么200㎡地图很小，SLAM仍可能占数百MiB以上

若地图的**包围矩形**为20m×10m、分辨率5cm，栅格为400×200=80000格；单字节occupancy约78KiB，4字节栅格约313KiB。面积相同但细长/分散户型的包围矩形可更大。这仅是输出栅格，不是完整SLAM。

运行中还要存扫描/子图、位姿图/边、空间索引、回环候选、优化器临时矩阵、代价地图与规划队列；视觉SLAM另有图像金字塔、描述子、关键帧和地图点。地图PGM文件几百KB不能推出运行SLAM只需几百KB。

按源需求5000点/圈、300rpm=5圈/s，假设内存中每点32字节：

```text
原始点历史 = 5000 × 5 × 32 × 1800秒 ≈ 1.44GB ≈ 1.34GiB
```

这还没计容器、索引和优化临时数据。如果连续30分钟原始扫描全保留，768MiB的2D预算就不成立。应按算法需要做采样/节点裁剪、限定最近扫描窗口、限制全局优化峰值、限制搬移重定位与地图保存时的复制；不能任意丢弃会破坏定位精度的数据。

slam_toolbox官方说明了扫描/位姿图、序列化和有界定位滚动窗口；ORB-SLAM3官方支持视觉、视觉惯性和多地图，但没有提供可直接套用于F20的固定RAM数字。因此本篇SLAM MiB数值是项目预算，**不是引用这些项目的最低内存要求**。参见[slam_toolbox](https://github.com/SteveMacenski/slam_toolbox)、[ORB-SLAM3](https://github.com/UZ-SLAMLab/ORB_SLAM3)，retrieved_at=2026-10-21。这里只用于解释算法资源构成，不表示已选型/已移植。

### 5.2 媒体缓冲敏感性

1080p NV12一帧约2.97MiB；RGB888一帧约5.93MiB；640×480灰度约0.293MiB。RAW/ISP中间帧、编码参考帧、缩放/畸变校正及CPU/NPU格式转换可能各有buffer队列。PMZ里已分配的帧与同一dma-buf引用不重复计量；真实新增拷贝需要计入。

4Mbps码流10秒只约5MB，但不能用此替代整条摄像机DDR预算。双屏像素缓存较小，SLAM、原始帧及模型通常更重要。

### 5.3 2GiB成本优化候选：可争取，但必须达到限额

上述2752MiB是较宽裕的并发预算，不是F20已测占用，因此不能仅据它宣布2GiB必然不够。若产品冻结为2D激光SLAM、云端对话、有限视觉模型，并投入零拷贝/队列/图历史优化，可设下列更严格目标：

| 项目 | 目标上限MiB | 相对宽裕预算需做的工作 |
|---|---:|---|
| Linux/基础服务 | 256 | 原生生产服务、裁剪调试/重复常驻进程；共享库/PSS对账 |
| 固件/no-map/PMZ等保留 | 384 | 保留现有350MiB PMZ依据，不凭空删除保留区；最终DTB复核 |
| 池外媒体/连续内存 | 96 | 尽量复用已计入PMZ的物理buffer、限队列/格式拷贝，实际ION/CMA另核 |
| 视觉模型及用户态工作区 | 128 | 限小模型常驻数量与输入/批次，禁无界缓存/同时加载多个大模型 |
| AFE/云端语音 | 48 | 有界环形缓冲/音频队列；不含重型离线ASR/TTS/LLM |
| 双屏UI | 16 | 控制动画/字体/解码缓存，无完整桌面 |
| 应用/网络/云 | 128 | 控制连接、线程栈、上传/码流队列，避免重复缓存 |
| 2D SLAM与导航峰值 | 256 | 由算法owner证明扫描/图/索引/优化峰值有界；地图不是只算PGM |
| 其余同时瞬态 | 128 | 地图更新流式落盘、模型串行切换；不能把各模块峰值错峰当作产品默认条件 |
| 合计目标 | **1440MiB** | **全项未实测，不表示已可达到** |

2GiB×75%=1536MiB，目标1440MiB还剩96MiB预算间隙，并保留约25%物理余量。这里最难关闭的是**SLAM 256MiB峰值、视觉128MiB和媒体buffer复用**。框架、全局回环/搬移重定位、地图保存复制、泄漏或更多算法可能立即突破。

准入建议：

1. 算法冻结为有界2D激光SLAM＋里程计/IMU，不将视觉/视觉惯性SLAM、稠密地图、完整ROS2开发栈或常驻LLM混入这张表；需要这些功能则重新预算。
2. 在最大场地/节点数、搬移重定位/回环、TF录制＋APP视频＋目标跟随＋音频/云并发时，对账不可回收页、PMZ/CMA及池外工作区，证明整机物理高水位满足1536MiB级目标和连续分配条件。
3. 需要错峰的操作必须由产品确认可接受，并有资源预留/降级合同。例如模型更新允许短暂停检测，不得偷偷暂停导航或让安全行为依赖云端。
4. 运行至少需求规定的72h长跑和重复启停/地图加载/网络断连/坏卡测试，无OOM、持续swap、图历史/队列无界增长和不可接受的导航/媒体长尾。
5. 最终2GiB料号及训练/DTB/固件须单独验证。8GiB开发板上人为限制进程内存可做前期压力实验，但不替代真实2GiB硬件的保留区布局、训练和DMA限制验证。

在满足上述证据后，2GiB可以重新评为量产成本版；当前推荐状态为“**2GiB待优化验证，4GiB标准基线，8GiB端侧AI/较重SLAM候选**”。eMMC不会因为DDR减到2GiB就自动可以减到8GB，系统、OTA、模型和地图仍单独预算。

## 6. 端侧语言模型方案的额外DDR

本节用Qwen3-1.7B和Qwen3-4B的公开结构做容量例子；**不是模型选型、A123X已转换可运行或速度保证**。参数数按1.7B/4B取整预算，实际模型及量化文件需替换；INT4纯权重另加25%格式/尺度等余量，再单独计算KV和工作区。

```text
纯权重字节 ≈ 参数量 × 权重位数 / 8
KV字节 = 2(K和V) × 层数 × KV头数 × head_dim
       × token数 × 每元素字节 × 并发batch
```

INT4权重**不表示KV也是4bit**。此处KV采用2字节、batch=1、4096 token；同一模型上下文升到8192，KV约翻倍。采用KV量化/窗口压缩必须由运行库支持并验证精度，不提前扣除。

| 项目 | Qwen3-1.7B结构例子 | Qwen3-4B结构例子 |
|---|---:|---:|
| 层数/KV头/head_dim | 28 / 8 / 128 | 36 / 8 / 128 |
| INT4纯权重MiB（取整参数预算） | 810.6 | 1907.3 |
| 加25%权重格式预算MiB | 1013.3 | 2384.2 |
| 4k上下文FP16/BF16 KV MiB | 448 | 576 |
| 运行/激活/暂存预算MiB | 512 | 768 |
| LLM额外峰值MiB | **1973.3** | **3728.2** |
| 加2D SLAM基础场景后峰值MiB | **4725.3** | **6480.2** |
| 保留25%余量后的物理容量 | **6.15GiB** | **8.44GiB** |
| 配置判断 | **8GiB候选** | **16GiB评估档** |

结构依据：[Qwen3-1.7B官方config](https://huggingface.co/Qwen/Qwen3-1.7B/raw/main/config.json)、[Qwen3-4B官方config](https://huggingface.co/Qwen/Qwen3-4B/raw/main/config.json)，retrieved_at=2026-10-21。KV和内存数值为本篇按公开结构计算，官方config没有承诺上述A123X运行内存。

如改为视觉SLAM，再加约768MiB，1.7B场景峰值约5493MiB、含余量约7.15GiB，8GiB仍只有受限余量；再加较重框架/离线ASR/TTS或更长上下文就可能需要16GiB。模型热切换时若旧/新模型同时驻留、多个对话并发、启用图像编码器，都需新增预算。

即使RAM容量可满足，也要测ADLA3转换覆盖/CPU回退、tokens/s、首token时延、持续带宽和电池功耗；传统SLAM的图优化不会因有NPU自动迁移。建议F20先用单个有界小模型，并能在资源不足时暂停非关键AI任务，导航与安全线程保持可用。

## 7. eMMC容量：系统、OTA、模型、地图分开算

### 7.1 当前8GB参考布局

当前F20_EVT1分区表固定有效载荷合计2406MiB，另有起始位置/对齐/gap，约2.36GiB级；其中system=2GiB、vendor=256MiB。data占剩余。

该值是**分区容量，不是实际已安装文件大小**。当前工作区相关构建输出随切板/清理变化，本次未取得可绑定当前完整F20来源的rootfs/OTA/模型资产清单，因此没有将旧包大小用作实测占用。8GB设备的实际用户区也不保证正好8×10^9字节，更不等于8GiB。

### 7.2 标准版持久存储预算

以下是面向后续可靠升级的容量预留方案，**尚未修改或实施A/B分区**；如果最终采用recovery单槽/流式升级，应单独证明坏包/掉电/失败恢复后再裁剪空间。

| 内容 | GiB预算 | 口径 |
|---|---:|---|
| boot/recovery/env/元数据/对齐 | 0.25 | 包含当前小分区及增长，不含原始core长期保留 |
| system A | 2.00 | 根文件系统槽预算 |
| system B容量预留 | 2.00 | 用于候选回退设计，不宣称现已A/B |
| vendor/runtime两槽合计 | 1.00 | 若vendor不独立双槽，需明确版本配套及回滚契约 |
| 视觉/音频/导航资源 | 1.00 | 仅计未已放入system/vendor的额外资产，不重复计算 |
| 有界地图、配置、校准、绑定 | 0.50 | 当前地图/上一良好版本/更新临时文件；超限需分层/裁剪 |
| 有界日志/诊断 | 0.50 | 日志轮转/限额；原始录像/rosbag/core不无限写入 |
| OTA下载暂存上限 | 3.00 | 若实际包/多包并存超过此值，重算；不在DDR保存整包 |
| 合计使用预算 | **10.25** | 不含常态用户录像 |

要求至少20%实际用户区保持空闲，则：`用户区 >= 10.25/0.8 = 12.8125GiB`。因此16GB为合理候选档，实际容量/文件系统保留和未来资产还需核验；8GB不足以同时满足该预算。

20%是项目空间余量策略，不是eMMC器件额外隐藏OP的测量，也不保证寿命。数据区满盘保护、写放大、随机写/同步写、磨损和掉电恢复分别验证。

### 7.3 本地语言模型的eMMC增量

模型版本升级需要当前/候选两份资产，容量槽位应覆盖转换后文件、词表/配置和完整性元数据；不依赖仅纯INT4理论权重。

| 场景 | LLM额外存储预算 | 加标准版后的使用预算 | 20%余量所需用户区 | eMMC档位 |
|---|---:|---:|---:|---:|
| 无常驻LLM | 0 | 10.25GiB | 12.81GiB | **16GB** |
| 约1–2B模型，当前/候选各2GiB | 4GiB | 14.25GiB | 17.81GiB | **32GB** |
| 约4B模型，当前/候选各4GiB | 8GiB | 18.25GiB | 22.81GiB | **32GB起** |

如同一模型已完整包含在A/B槽内，应从上述额外模型槽减去重复部分；如多语言离线ASR/TTS、多模型、多楼层大地图/视觉atlas、长期离线内容要求增加，则按实际资源包重算，可能升64GB。重型4B方案推荐16GiB DDR并不自动意味着eMMC也必须64GB，两者依据不同。

### 7.4 SLAM地图、原始数据和录像的持久化策略

2D栅格本身很小，但可继续建图/重定位所需的posegraph/扫描/视觉atlas可能远大于PNG/PGM。默认保留当前/上一良好地图及更新临时版本，按总字节、图节点/关键帧数、每地图及总地图数设限；地图更新使用原子发布和版本兼容检查，断电后保留可用旧版本。

原始传感器包/rosbag/持续关键帧图像默认不在eMMC常驻记录：用TF或按需受控导出，并限制时长。TF不在/满/坏时关闭对应录制能力并报告，不无界转写eMMC，导航定位所需地图保留在本机可靠存储中。

4Mbps仅作码率例子：录像约1.8GB/小时、43.2GB/天，音频/容器另加；不是F20已批准码率。eMMC 16/32GB都不适合作为常态长时间录像容量。TF标称256GB按4Mbps纯视频理论约142小时，实际更少，需扣格式、音频、预留及循环策略。

## 8. 容量之外必须同时满足的条件

- LP4X 32bit×4266MT/s理论峰值约17.064GB/s，是总线数据率上界，不是应用实测带宽，也不能读写各算一份17GB/s。双NPU/ISP/编码/CPU/SLAM同用DDR，需测竞争、QoS和温度。
- 当前图面4GiB换8/16GiB涉及料号球图、rank/容量检测、训练、时序、电压及固件，不能只修改DTS内存大小；eMMC换容量也要核QVL、总线/电压、容量识别、GPT脚本实际调用和全盘备份GPT。
- 更大容量不保证随机写/同步写、加载时延、寿命或功耗改善；采购需核供应生命周期/PCN、温度等级、擦写寿命和可靠写特性，不沿用原图老料号推定量产可采购。
- 云端对话掉线时的降级行为和端侧模型是否常驻决定实际峰值；容量预算不能替代产品体验/语音准确率评审。

## 9. 容量冻结前的验证门槛

下列是待批准验收建议，不是本次测试结果：

| 场景 | 需要观测 | 建议关闭条件 |
|---|---|---|
| 空闲/启动及模型/地图冷加载 | 实际物理DDR、MemTotal/MemAvailable、PSS、reserved/CMA/媒体池、加载峰值 | 对账物理页且无重复统计，启动/加载不超过预算 |
| 200㎡30min建图，至少对应最大节点/关键帧数 | 扫描/图/索引/求解器峰值、队列增长及地图保存 | 最大历史/复制有界，SLAM峰值满足相应档位 |
| 搬移重定位/闭环/全局优化/地图重载 | CPU长尾、内存瞬态、导航/音视频时延 | 满足批准的20s重定位/重规划及媒体目标，不因内存回收阻塞 |
| SLAM＋跟随＋1080p预览/TF＋音频/云＋UI并发 | 系统物理占用、CMA最大分配、NPU/DDR竞争、热/功率 | 高水位仍留约定余量，无OOM、持续swap/异常回收和队列增长 |
| 端侧LLM 4k/8k、冷加载/连续对话/模型切换 | 权重实际占用、KV、prefill/decode工作区、CPU fallback、首token/速度 | 真实额外峰值和余量符合8/16GiB条件，未达标缩模型/上下文或升档 |
| 资源升级、OTA、地图原子更新、坏卡/满盘 | 实际镜像/包/模型体积、当前+候选+临时共存、空闲阈值 | 最坏时实际用户区≥20%空闲；恢复/保数据按正式方案验证 |
| 至少覆盖需求72h长跑与重复地图/模型/连接启停 | PSS/Slab/DMA池/FD/线程/图节点/磁盘写入趋势 | 无无界增长；出现增长先定位泄漏/历史保留，不仅用加内存掩盖 |

板端采集优先只读：`/proc/meminfo`、`/proc/<pid>/smaps_rollup`、`/proc/pressure/memory`（如内核支持）、实际DTB/`/proc/iomem`和厂商媒体池统计。dma-buf debugfs若未挂载，不在只读采集中擅自挂载或更改内核参数。分区识别先从sysfs/`/proc/partitions`核设备，未确认MMC类型不盲对某个mmcblk写操作。

报告把可回收缓存、不可回收页、共享DMA、no-map及统计缺口分开；峰值采样覆盖事件窗口，不能仅用分钟级平均值或空闲free输出证明容量。
