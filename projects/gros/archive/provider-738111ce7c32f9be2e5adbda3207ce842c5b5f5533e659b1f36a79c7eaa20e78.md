## 核心结论

扫码后count=1与配置文件仍为空并不矛盾：当前实现存在不同的状态来源，Sensor的保存网络缓存不是磁盘配置的证明。

| 层 | 实际行为 | 重启可保留吗 |
| --- | --- | --- |
| Sensor saved_network_cache_ | 可由扫码成功后的凭据直接插入 | 否，内存vector |
| API stConnectContext.stConnectParam | VSAPIWIFI_SaveNetwork仅复制凭据到内存 | 否 |
| supplicant运行时LIST_NETWORKS | 由控制命令配置的运行态网络 | 仅运行时存在不证明落盘 |
| supplicant实际配置文件 | 依赖成功SAVE_CONFIG及正确路径、配置权限等 | 保存成功才支持下次加载 |

## 已核实的实现问题

1. API SaveNetwork的成功不是持久化成功。
   - modules/api/src/api_network/api_wifi.c:3253开始的VSAPIWIFI_SaveNetwork只校验参数、安全类型，锁定连接上下文后memcpy并返回成功，日志Network saved locally。
   - 没有文件写入、没有SAVE_CONFIG，也没有验证配置文件。公共头没有对这个边界作说明。
2. Sensor会据此将扫码凭据直接写入保存网络缓存。
   - sensor_wifi_service.cpp:2354-2414的saveConnectedCredential调用上述API；API返回成功后更新或插入cache，设置valid=true。
   - 所以cache count=1可能只是扫码凭据的内存投影，无法证明supplicant落盘。
   - 历史6935f84存在相同的核心cache更新逻辑；现场banner及日志仅辅助映射，仍缺ELF身份绑定。
3. 已连接时所谓定期刷新可能永远命中自身缓存。
   - handleMonitorState已连接分支4510起调用getSavedNetworks(...,true)。
   - getSavedNetworks在prefer_cache且valid时直接返回；没有缓存年龄或TTL。因此该调用不是对后端的周期复核。
   - 当前API GetSavedNetworks读取的是supplicant LIST_NETWORKS及运行态network配置，本身也不等于读取磁盘。
4. 空配置文件不会被兜底初始化。
   - linux_common.c:1033起ensure_wpa_config_file，在access(F_OK)==0时直接返回。零字节文件也满足存在检查，不会写入默认ctrl_interface/update_config等字段。
   - API api_wifi.c:68起_WIFI_EnsureSupplicantConfig有同样的存在即跳过逻辑。
   - 当前modules/wifi/lib.mk:15设置WMG_CONFIG_PATH=/data/etc，默认文件名/wpa_supplicant.conf，组合默认/data/etc/wpa_supplicant.conf。
   - API兜底路径为/etc/wpa_supplicant.conf；现场是否为软链接/同一文件以及wifimg配置是否覆盖文件名，尚未核实。
5. 底层保存失败未形成上层明确的持久化终态。
   - linux_sta.c:1610起SAVE_CONFIG失败仅warning，仍继续选择网络。
   - linux_sta.c:2722起连接成功调用wpa_conf_enable_all_networks，却忽略返回值；该函数916起SAVE_CONFIG失败返回FAIL。
   - Sensor handleConnectedState:3902也忽略saveConnectedCredential返回值；保留已连接链路可以合理，但缺少独立保存失败状态。

## 现场对应

- lei_2 sensor.log:3375为SET_PROVISION_CREDENTIAL，3390-3394连接成功；3397起cache count=1。
- 用户确认上传时conf仍为空，比仅看到采集包零字节文件提供更强现场证据。
- 最吻合的候选路径：实际配置为空且被存在检查放行；扫码设置运行态network并连接；持久化未成功或保存到其它路径；API内存SaveNetwork仍成功，Sensor cache变1；下次启动后端没有可恢复条目，等待重新扫码。
- 链路中的内存更新、空文件跳过及错误传播缺口是源码已证实事实；现场SAVE_CONFIG是否失败、失败原因及实际加载路径仍未知，不能宣布完整根因已经闭环。
- 不能把33分钟扫码前等待全部归为自动恢复失败：用户测试是否预期自动联网、是否有意清空配置尚未限定；本次直接审查的问题是扫码成功后conf仍为空和保存缓存语义。
- 空缓存不会永久阻断所有直接查询：未连接且无保存网络时，handleMonitorState:4522起仍周期调用prefer_cache=false的查询。不要将反复cache INFO日志解释为完全没有后端复查。

## 建议修复边界及验收

- WiFi：在启动supplicant前校验真实配置文件；对已确认零长度文件可安全补全默认头，写入需检查错误并保留非空用户配置，不能盲目覆盖已有网络或把解析异常一律重建。
- WiFi/API：由配置owner提供真实路径和SAVE_CONFIG结果；将运行时凭据缓存与持久化确认分开，记录脱敏的大小、网络数、来源和返回码。文件大小非零也不是单独的网络持久化证明。
- Sensor：cache区分本地凭据、后端快照与持久化确认，记录新鲜度；在稳定且无连接/扫描冲突时有界复查。不能仅改prefer_cache=false就声称已验证落盘。
- 保存失败保持当前链路可用，独立报告store失败或待重试，有限重试；不将保存失败伪报为断链，不为修复缓存发起清空网络或无证据reset。
- 验证至少覆盖：零文件启动、正常文件保留、写失败但链路可用、扫码后后端条目与落盘确认、正常重启免扫码恢复、同版本测试OTA保留网络；Host测试和设备重启/OTA结果分别记录。
