# WiFi 扫描契约消费者兼容性审计

范围：当前工作区可见生产源码；递归搜索 GetScanResults、按 SSID/band 查询、ScanStart、底层 wifi_get_scan_results；排除旧 .worktrees、构建输出、生成 protobuf、头声明和 Host stub。第三方源码附加搜索未发现同名消费者。仅只读，没有修改生产代码、构建、设备或 Git 写操作。

结论：上一轮恢复 scan_action 的只读结果语义时，遗漏了业务消费者兼容性。除用户指出的 pt_common，还发现 pt_hw_wifi 老化扫描和受 SUPPORT_LINKD 宏控制的 wifi_daemon 配网入口。不得宣称所有消费方已适配。

## 必须适配

1. app_product_test/pt_common.c:2821-2854，_PT_WifiScanCacheRefresh 直接 GetScanResults，启动连接前与周期覆盖刷新都未 ScanStart。无缓存可能保存空结果并视为刷新成功，启动重试因此提前停止；有旧缓存则更新时间戳伪装本次新扫描，2.4G/5G覆盖/RSSI可能陈旧。调用方位于 3043/4046。
2. app_product_test/pt_hw_wifi.c:79-154，_PT_WifiAgingScanLocked 仅在已断开/未扫描时 GetScanResults，没有 ScanStart。无缓存一直不通过；有旧缓存时 count>0 即永久置 bPassed，可能未执行本次主动扫描便通过。
3. modules/wifi/deamon/wifi_daemon.c:1978/1986/2101，cmd_handle_p 的数组清零，未设置 scan_action=true，也无缓存未命中后的主动扫描。配网后安全类型探测变成仅查缓存，目标不存在时沿默认 WPA2 连接；需显式 true 或缓存未命中后主动扫描。仅 SUPPORT_LINKD 编译启用才进入，未验证产品是否构建此 daemon。

## 已按现有契约处理/需说明边界

- wifi_daemon cmd_handle_s:1049 明确 scan_action=true；普通 connect cmd_handle_c:1340 先 false 缓存，1407 未命中后 true，均无需无条件补扫描。
- API _WIFI_DetectWmgSecurity:1444 原本就是 false 先查缓存，第二遍 true，正在扫描时不抢 owner；不是遗漏。
- Sensor monitor:4477 发 ScanStart，3780 完成事件后取结果；credential-security:5212 发起/复用已有扫描，5287 完成后读结果；没有同类遗漏。
- Sensor connectWifi:3037 的无排队安全信息兜底 -> detectSecurityMode:4862 -> readSecurityModeFromScanResults:4897，确实只读缓存。未命中会用最近安全缓存或既有 credential fallback，而不主动扫描；新契约下更依赖上游 resolveSecurityModeForCredential 主动扫描结果。应视为待覆盖的兼容边界，不能承诺该兜底仍自动扫描，也不能把它与完整 credential scan worker 等同。getScanResultBySsidFromApi 仅有定义，没有生产调用点。
- API GetScanResultBySsid:2946/2971 与 GetScanResultBySsidAndBand:3004/3029 都直接包装 GetScanResults，因此也变成缓存查询，无内部扫描兜底。当前可见源码没有额外活跃业务消费者，未覆盖预编译应用或外部 SDK 消费方。公共头未明确描述结果查询 freshness/无隐式扫描，需要补齐文档契约。

建议：产测 common 与 aging 分别补显式扫描和真实终态处理，空结果与本次成功扫描区分，不能将缓存读取时刻当采样时刻；不要在高频/共享回调无界阻塞。daemon linkd 补主动刷新，Sensor 无排队安全信息兜底明确是否要求新鲜扫描并增加回归。保留 ScanStart session 唯一 owner、BUSY、取消与迟到终态规则，GetScanResults 不全局恢复隐式扫描，避免重现双扫。
