## 发现 F1：P1，并发快照仍使用共享 strtok，已复现

- 位置：modules/wifi/wifimanager/core/src/os/linux/linux_sta.c:189、247、351、360；MAC/IP 与多个网络列表解析也使用 strtok。
- STATUS 与 SIGNAL_POLL parser 的 token 游标共享。普通命令互斥仅覆盖控制命令收发，不覆盖调用后的解析；独立限时查询本身不经过普通控制连接锁。
- wifimg.c:317-320 的 info_snapshot 直接进入 linux_sta_get_info_snapshot，绕过 action 队列；API api_wifi.c:737 在独立采样路径调用它。连接流程仍在 action 上解析 STATUS，事件/DHCP 和保存网络查询也可能解析。
- blame：解析逻辑可追到仓库根提交 9d341f0；并发快照入口由 bf8d227e4184d5e2300da0eb522f75fd3c44d83f 于 2026-09-29 引入，API 调用由 c86d964 引入。不能把问题归为 2026-10-16 三个末次提交新写入的 strtok。
- 临时 harness 包含当前完整 linux_sta.c 与实际 scan.c，使用两个线程及条件变量，确定性安排 STATUS 第一 token 之后、下一个 token 之前运行 SIGNAL_POLL parser。原 strtok 保留，仅加调度包装；不访问设备或网络。
- 结果：STATUS ret=0，但 SSID 长度=0，预期长度8。属于真实源码行为的受控交错复现，不是设备发生频率测量。
- 影响：wpa_check_connected_ssid() 目标确认失败，可能再次出现已关联/已有 DHCP 却 Connect 不成功；新 kernel IPv4 查询不修复 SSID token。API 对空 SSID 保留旧 acSsid（api_wifi.c:791 附近），也可能把不完整采样包装为成功，需一并定义有效字段。
- 建议：逐函数改为局部游标/有界逐行解析，保持独立查询通道；不要退回全局串行大锁，避免重现长队列阻塞。补 STATUS/SIGNAL/列表并发行为测试。

## 发现 F2：P2，合法 SSID 边界错误，已复现

- linux_sta.c:189 使用分隔集合 "'\n'"，单引号也被当作分隔符。合成 SSID O'Reilly 被解析为长度1，返回成功，随后精确身份确认必然不匹配。
- linux_sta.c:211 将 decoded_len < SSID_MAX_LEN 作为接受条件，SSID_MAX_LEN=32，恰好32字节被拒绝（复现ret=-6）。相似判断还存在保存网络列表路径：554、826、3275附近。
- 它们是历史遗留，不是本轮 IPv4 复核引入。有限重试无法修复每次都确定错误的解析。
- 建议：只按真实行边界拆分，按原始 SSID 字节/后端转义契约解码，允许32字节；不 trim、截断或弱化目标身份比较。补单引号、32字节、多字节与转义边界。

## 发现 F4：P2，连接总耗时仍非硬上界，静态确认

- api_action.c:73 act_transfer_wait 使用 OS_NET_WAIT_FOREVER，普通控制连接获取 pthread mutex 也没有总 deadline。
- linux_sta.c:2601 在配置网络和 try_check_udhcpc 之后才设置 connect_start；u32TimeoutMs 约束的主要是事件等待循环。
- Sensor 在提交 API 前重算剩余预算，但无法中断已经进入的同步 vendor/action；不能把30秒局部 timeout宣传为30秒必定返回。
- 建议：后续将排队、控制锁、配置命令、事件等待、取消/回收纳入同一单调 deadline。不可仅给同步等待加超时后释放仍在使用的栈参数；保持参数及 owner 生命周期。

## 最新优化的有效边界和反向风险

1. 已验证连接缺 IPv4 时最多约3秒复核，最后有效观测5秒 freshness；重读缓存不续期；明确终态、新请求和 shutdown 清理 pending。现有回归覆盖了自动候选及迟到扫描阻止、休眠准入和低功耗缓存推进。
2. 真实地址持续缺失会延后约3秒暴露，unknown持续约5秒会让业务linked失效。这是有界容忍的代价，不能无限延长以消除离线日志。worker若阻塞，也不能保证精确在第3秒执行。
3. API 将观测失败返回 BUSY，确认无地址返回 FAILURE+空IP，语义改善；查询频繁失败仍会耗尽 freshness，从而出现历史类似业务false。这时应修复失败来源，不能简单增大阈值。
4. 内核查询当前仅IPv4。IPv6-only、有IPv6但无IPv4时仍不满足当前业务linked契约；写注释不等于双栈支持。若产品需要双栈，应增加独立L2/IPv4/IPv6/路由/业务状态并验证IoT/TCPKA能力。
5. 内核非零IPv4不代表路由、DNS、网关或云服务可达，也不独立证明地址属于本次网络。目标身份确认仍须保留。
6. notifications overflow /扫描无终态的 STUCK 保留是故障安全措施，代价是服务保持降级、拒绝后续操作或休眠。禁止为了恢复表象而无依据清busy、detach或直接重置共享backend。
