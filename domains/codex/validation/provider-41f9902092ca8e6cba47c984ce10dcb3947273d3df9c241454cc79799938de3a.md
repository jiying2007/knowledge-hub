# 跨项目任务 intake 与 Provider 查询失败分层诊断

结论：非平凡任务的 intake 要求必须分发到全局受管规则，不能仅出现在 Knowledge Hub 项目规则中。其他项目只收到全局规则时，若仅在结束阶段调用 final gate，会因未登记真实任务而被阻断。任务应在取证或实施前使用 execution-policy ensure，登记并回读真实请求、准确当前线程、实际模式和验收项，再按真实证据、工件、checkpoint、目标完成与 final gate 顺序收口。

Provider 查询和 Execution Policy 是独立验收线。合法 general 查询曾返回 SCHEMA_INVALID，但同一输入在当前运行时已成功；现有失败回执不能确定历史内部校验原因，不应归因于任务类型、shell 转义或用当前成功替代历史失败。其他线程后续已有 intake，也不证明其原任务终态通过。

证据：Codex PR56，提交 d1844473a50db55119aa287253531e3d8629f93e，合并 dbe4c1d658b9ee3db551010c658f70f76c44fa15。三版本正式 CI 各438项测试零失败零跳过，隔离安装与回滚验证通过；实际安装后438项测试、四profile smoke与零变更复验通过。全局规则保持4456字节及原4500字节门禁。

风险：这是 Agent 执行约定，不是宿主隐式启动 hook；文件更新不证明已启动会话收到新规则或执行过 intake。缺少任务、证据或工件时仍应阻断。诊断者不得代填其他线程 journal、借用自己的 PASS 或生成追溯完成证明。历史 Provider SCHEMA_INVALID 的内部原因仍未确定。

复用步骤：先核对会话实际收到的全局与项目规则，再检查真实命令及原始回执的时间；读取准确线程的 intake 状态，分开报告原任务与后续任务。合法查询失败时保留有界诊断证据并定向复现，不盲目放宽 schema、路由或策略条件。本记录保持 reviewing 候选，不授予 active、Owner 或产品放行。
