# Operator governed apply receipt (P2.9)

P2.9 is a read-only post-apply verification layer for P2.8 governed evidence binding transactions.

It does **not** apply evidence and it does **not** perform rollback. Its job is to prove what P2.8 actually wrote, verify that the recoverable transaction material still matches the governed chain, and produce a deterministic rollback-readiness plan for a later, separate governance phase.

## Input

P2.9 consumes a saved JSON result emitted by a successful P2.8 governed apply.

```bash
tools/ci/python-runtime.sh -m tools.codex_assets.knowledge_hub.operator_binding_receipt_cli \
  --root . \
  --apply-result <saved-p2.8-apply-result.json> \
  --json
```

The receipt CLI is read-only and performs no provider discovery or network access.

## What is revalidated

P2.9 rejects the input unless the P2.8 result still asserts the exact governed write boundary:

- projection is `knowledge-operator-binding-governed-apply-v1`;
- apply status is `applied`;
- canonical write was explicit, not automatic;
- authorization was validated and not generated by the Operator;
- reviewer identity remains explicitly **not** provider-verified;
- the invoking operator acknowledged that identity boundary;
- owner/status/readiness mutation flags remain false;
- the only changed path is `registry/items.jsonl`;
- authorization, review-bundle, patch-plan, and proposal fingerprints have valid deterministic shapes;
- registry before/after/post-apply SHA256 values are coherent;
- all authorization rows were approved and none rejected.

It then verifies the actual transaction material on disk:

- transaction id is derived from the exact authorization fingerprint in the same way as P2.8;
- journal path is the exact `.tmp/transactions/<transaction-id>/journal.json` path;
- journal status is `applied`;
- journal contains exactly one changed write to `registry/items.jsonl`;
- journal before/after/expected SHA256 values match the P2.8 result;
- applied paths contain only `registry/items.jsonl`;
- no rollback path is recorded for the successful transaction;
- the `before/registry/items.jsonl` backup exists and hashes to the exact P2.8 before-SHA.

A malformed/tampered journal, missing backup, backup hash mismatch, widened write scope, or upgraded identity claim fails closed with `status=blocked`.

## Receipt fingerprint

For a structurally valid P2.8 transaction, P2.9 emits a deterministic `receipt_fingerprint` over immutable transaction facts:

- transaction id;
- authorization fingerprint;
- review-bundle fingerprint;
- patch-plan fingerprint;
- selected proposal fingerprints;
- registry before SHA256;
- registry after SHA256;
- journal SHA256;
- before-backup SHA256.

The current registry SHA is intentionally **not** part of this fingerprint. This means later legitimate repository changes can change rollback readiness without changing the historical identity of the original governed apply transaction.

## Current-state observation

After verifying the transaction chain, P2.9 observes the current `registry/items.jsonl` SHA256.

If it still exactly matches the P2.8 after-SHA:

- receipt status is `verified-current-post-apply-state`;
- `rollback_ready=true`;
- the rollback plan records the exact current SHA that a later rollback must confirm and the exact before-SHA that would be restored.

If it no longer matches:

- receipt status is `post-apply-state-drift`;
- the historical receipt remains valid;
- `rollback_ready=false`;
- the rollback plan status is `not-ready-current-drift`.

This is deliberate: an older backup must never overwrite later registry work just because the original transaction was once valid.

## Rollback boundary

P2.9 emits a **plan only**. It does not restore the backup.

The plan requires a separate governed rollback phase and an explicit re-confirmation that the current registry SHA is still exactly the P2.8 after-SHA immediately before any restore operation.

The plan also preserves these non-negotiable rules:

- do not rollback if `registry/items.jsonl` changed after the governed apply;
- do not infer owner revocation from filesystem rollback readiness;
- do not overwrite unrelated registry changes;
- do not treat a receipt as external identity-provider verification.

`reviewer_identity_provider_verified=false` remains true as a statement about the trust boundary: P2.7/P2.8/P2.9 validate deterministic authorization data and explicit operator acknowledgements, but do not authenticate the human owner through an external identity provider.

## Automatic execution remains disabled

P2.9 is report-only:

- `read_only=true`;
- `canonical_write_performed=false`;
- `automatic_binding_enabled=false`;
- `automatic_execution_enabled=false`;
- `rollback_performed=false`.

P2.9 does not mutate the real canonical registry while being tested. Repository branch protection and product terminal closure remain separate governance concerns.
