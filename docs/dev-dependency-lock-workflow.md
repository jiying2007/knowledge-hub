# Development dependency lock workflow / 开发依赖锁维护

## Contract / 合同

- `requirements-dev.txt` is the reviewed **direct dependency pin** set.
- `requirements-dev.lock` is the reviewed, hash-locked **universal resolution**, generated by `uv pip compile requirements-dev.txt --universal --python-version 3.10 --generate-hashes --output-file requirements-dev.lock`.
- `requirements-runtime.txt` and `requirements-runtime.lock` are a distinct production/runtime contract; development upgrades must not silently rewrite them.
- `pyproject.toml` build backend version must be consistent with the matching direct `setuptools` pin and its lock entry.
- Fail closed: do **not** waive the direct-version/lock checks, substitute synthetic hashes, remove `--require-hashes`, or merge with a failing Quality or Security approval gate.

## Updating / 更新流程

1. Change the directly pinned package version(s) in `requirements-dev.txt`; align build backend in `pyproject.toml` if relevant.
2. Open a branch and PR. The read-only `dev-dependency-lock-candidate` workflow checks out the exact PR HEAD and uses the SHA-pinned `setup-uv` action with a fixed uv version. It resolves a fresh universal hash-locked candidate.
3. On mismatch, the candidate workflow fails, but preserves the generated lock as a short-retention PR artifact. Download and verify that artifact, then commit its **exact contents** as `requirements-dev.lock` on the same PR branch. Do not copy only a new direct pin without its hashes and transitive resolution.
4. After committing, the candidate workflow must reproduce exactly the committed lock (`cmp`), and Quality must independently install the hash-locked dependencies and pass its full engineering, security, regression, and evidence gates.
5. An exact-head security-critical PR change requires the existing hash-bound owner approval. A general discussion approval never substitutes for a matching exact-head approval.
6. Use a guarded expected-head merge, then verify **fresh master** Quality, Signed and branch hygiene before closing superseded dependency PRs.

## Safety / 安全边界

The candidate workflow has `contents: read` only. It does not read provider credentials, write branches, auto-approve, or auto-merge. Its output is a **proposal artifact**, not authority to deploy.

The workflow does not replace official package provenance review, security advisories, or tests on the supported Python versions. A hash verifies the selected published artifact bytes, not whether upstream code is safe.

## Failure recovery / 失败恢复

- Candidate resolution fails: keep the PR open and examine the workflow log; do not fill a hash by guessing.
- Candidate differs: commit the generated lock and rerun checks. If unrelated transitive packages changed, review the complete diff and explain the reason.
- Quality fails after a dependency upgrade: fix incompatibility or revert the particular upgrade and regenerate from the resulting direct manifest.
- A PR goes stale: refresh its HEAD and exact checks; never reuse a prior PR's success or security approval for a different SHA.

## Acceptance / 验收

The generated lock must equal the committed lock byte-for-byte; all required checks must pass for the final PR HEAD; fresh protected-master verification must succeed. Real product/owner/connector/production evidence remains an independent qualification boundary.
